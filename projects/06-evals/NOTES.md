# NOTES — 06 evals (the shared gate)

> Raw material for the blog — candid about what broke and how it was fixed.

## Goal
Consolidate evaluation into one reusable gate that wraps `shared/eval.py` and every
project reports against: classification accuracy + a 1-5 rubric judge (judge = a
SEPARATE stronger model to reduce self-bias). Establish baseline scores; pin down
judge stability and contamination discipline.

## Baseline (one official run)
**Track A — classification accuracy (12 tickets):**
| model | acc |
|---|---|
| kimi-k2p6 | 100.0% |
| deepseek-v4-pro | 91.7% |
| kimi-k2p5 | 91.7% |
| glm-5p1 | 91.7% |
| gpt-oss-120b | 91.7% |

**Track B — rubric judge (deepseek drafts, gpt-oss-120b judges, 3 runs):**
3.50 / 3.58 / 3.58 → **3.56 ± 0.039** (1-5).

## Steps taken
1. Wrote `run.py` as the gate: it shells out to `shared/eval.py` for both tracks so
   there's exactly one scoring implementation in the repo (no re-implementation).
2. Track A across all catalog models; Track B drafts with one model and judges with a
   different, stronger one (`--judge-model`), run K=3 to measure judge stability.

## Challenges / findings
- **The judge is stable in aggregate, noisy per item.** Across 3 full runs the mean
  judge score moved only ±0.039 — yet we know from projects 00/01/02 that individual
  outputs (and single-ticket judge scores) wobble run-to-run because these MoE reasoning
  models aren't deterministic even at temperature=0. The lesson: **report the aggregate
  over the whole split (and ideally average a couple of runs); never gate on a single
  per-item judge score.** Averaging 12 tickets washes out the per-call noise.
- **Use a different model to judge than to answer.** deepseek drafts, gpt-oss judges.
  Same-model judging inflates scores (a model likes its own style); separating them is
  cheap insurance against self-bias and is the gate's default.
- **`--max-tokens` is the gate's foot-gun.** `shared/eval.py` defaults to 64; for these
  reasoning models that silently zeroes classification accuracy (the project 00 trap).
  The gate pins 1024 for reasoning models. A harness that hides max_tokens will quietly
  mis-measure reasoning models — surface it.
- **Dependency noise:** since project 05 pulled eval-protocol (→ newer fireworks-ai,
  pydantic v2), runs now print a benign `Core Pydantic V1 ... Python 3.14` UserWarning
  from openai's compat shim. Cosmetic; results unaffected. (Reinforces: the training/eval
  tools really want their own venv.)

## Contamination discipline (the thing that makes these numbers trustworthy)
- **`data/tickets.jsonl` (12 tickets) is the FROZEN eval split.** It is the gate's only
  test set and is used unchanged by every project.
- **Nothing trains on it.** Projects 04 (SFT) and 05 (RFT) trained on *synthetic*
  data (`train.jsonl` / `rft_train.jsonl`, 96 examples each) that was explicitly
  de-duplicated against the eval inputs. So the +16.6 (SFT) and +16.7 (RFT) gains are on
  genuinely held-out data, not memorized rows.
- **One honest wrinkle:** the synthetic train data was generated by gpt-oss-120b, which is
  also a catalog model and one of the judges — there's a soft stylistic overlap. It's not
  train/test leakage (different examples), but worth naming: a fully clean setup would use
  a generator outside the eval/judge model set.

## Cost
- ~1.9 min wall clock: 5×12 classification calls + 3×(12 draft + 12 judge). `shared/eval.py`
  runs concurrent (semaphore), so the gate is fast. Pricing TODO still tracked for 08.

## Learnings (2-3)
- **Gate on aggregates, not items.** The judge mean is stable to ±0.04; any single
  ticket's score is not. Build the gate around the split-level metric.
- **Separate judge model + pinned max_tokens are non-negotiable defaults.** One prevents
  self-bias, the other prevents silently zeroing reasoning models. Both are baked into the
  gate so no downstream project has to remember them.
- **Freeze the eval split on day one.** The whole portfolio's accuracy story (00 through
  05) is only credible because the 12 tickets were never trained on. Decide the test set
  before you fine-tune anything.
